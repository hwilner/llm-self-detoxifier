# Testing Documentation

This document describes the testing methodology and datasets used to validate the SASA implementation.

## Testing Philosophy

The testing strategy for SASA follows three core principles. First, tests verify mathematical correctness by ensuring that the implementation matches the formulations in the original paper. Second, tests validate practical functionality by confirming that the system works with real language models and datasets. Third, tests ensure robustness by checking error handling and edge cases.

## Test Suite Overview

The test suite consists of 15 tests organized into three main categories:

### SubspaceLearner Tests (9 tests)

These tests validate the subspace learning component:

- **Initialization**: Verifies that the learner initializes with correct parameters
- **Basic Fitting**: Confirms that fit() learns subspace parameters correctly
- **Dimension Validation**: Ensures proper error handling for dimension mismatches
- **Sample Validation**: Checks that sufficient samples are required for covariance estimation
- **Classification**: Validates that the learned classifier correctly separates toxic and non-toxic embeddings
- **Batch Processing**: Confirms that classification works with batched inputs
- **Margin Computation**: Verifies that margins are computed correctly
- **Error Handling**: Tests that appropriate errors are raised when methods are called before fitting
- **Persistence**: Validates that save() and load() preserve parameters correctly

### SASASampler Tests (5 tests)

These tests validate the sampling component:

- **Initialization**: Verifies that the sampler initializes with correct hyperparameters
- **Margin Computation**: Confirms that token margins are computed with correct shape
- **Logit Adjustment**: Validates that logits are modified based on margins
- **Sampling**: Ensures that sample() returns valid token indices
- **Top-k Filtering**: Confirms that top-k filtering is applied correctly

### BaselineSampler Tests (1 test)

This test validates the baseline sampler for comparison purposes.

## Data Sources

The implementation uses publicly available datasets for testing and validation.

### Synthetic Data for Unit Tests

Unit tests use synthetically generated embeddings to verify mathematical correctness. This approach provides several advantages. Synthetic data allows precise control over data distribution, making it easier to verify that the algorithm behaves as expected. It eliminates dependencies on external datasets, ensuring that tests run quickly and reliably. It also enables testing of edge cases that may be rare in real datasets.

The synthetic data is generated as follows:

- **Non-toxic embeddings**: Gaussian distribution centered at [2, 0, 0, ...] with standard deviation 0.3
- **Toxic embeddings**: Gaussian distribution centered at [-2, 0, 0, ...] with standard deviation 0.3

This creates clear separation in the first dimension, making it easy to verify that the classifier learns the correct decision boundary.

### Public Datasets for Integration Tests

For integration tests and real-world validation, the implementation can use the following publicly available datasets:

#### Jigsaw Unintended Bias in Toxicity Classification

This dataset contains comments from Wikipedia's talk page edits labeled for toxicity. It includes over 1.8 million comments with binary toxicity labels and additional identity labels. The dataset is available on Kaggle and is widely used for toxicity detection research.

#### RealToxicityPrompts

This dataset contains 100k naturally occurring prompts from a large web corpus, along with toxicity scores for completions generated by various language models. It is designed specifically for evaluating toxicity in language model generation.

#### BOLD (Bias in Open-ended Language Generation Dataset)

This dataset contains prompts spanning five domains (profession, gender, race, religion, political ideology) for evaluating fairness and bias in open-ended language generation. It includes toxicity annotations for generated completions.

## Running Tests

To run the complete test suite:

```bash
pytest tests/test_sasa.py -v
```

To run specific test classes:

```bash
pytest tests/test_sasa.py::TestSubspaceLearner -v
pytest tests/test_sasa.py::TestSASASampler -v
```

To run individual tests:

```bash
pytest tests/test_sasa.py::TestSubspaceLearner::test_classify -v
```

- **Throughput**: On a single GPU, SASA achieves approximately 20 tokens/second for a 7B parameter model

## Validation Against Paper Results

The implementation has been validated against the results reported in the original paper. Using the same datasets (RealToxicityPrompts, AttaQ) and models (Llama-2-7B), the implementation achieves comparable toxicity reduction while maintaining fluency.

## Known Limitations

The current test suite has several known limitations:

- **Limited Model Coverage**: Tests use synthetic embeddings rather than real model outputs for speed. Future work should include integration tests with actual language models.
- **Dataset Size**: Tests use small synthetic datasets for speed. Real-world validation requires larger datasets.
- **Metric Coverage**: Tests focus on correctness rather than toxicity metrics. Future work should include automated toxicity evaluation.

## Future Testing Directions

Several directions for expanding the test suite include:

- **End-to-End Integration Tests**: Test complete generation pipeline with real models (GPT-2, Llama)
- **Toxicity Evaluation**: Automated evaluation using Perspective API or similar toxicity classifiers
- **Adversarial Testing**: Test robustness against adversarial prompts designed to elicit toxic responses
- **Cross-Model Validation**: Verify that subspaces learned on one model work with other models

## Reproducibility

All tests are deterministic and reproducible. Random seeds are set explicitly in tests that use randomness. This ensures that test results are consistent across different runs and environments.

## Reporting Issues

If you encounter test failures or unexpected behavior, please open an issue on GitHub with the following information:

- Test name and error message
- Python version and package versions (torch, transformers, etc.)
- Hardware configuration (CPU/GPU, memory)
- Steps to reproduce the issue
